# Part 11 — Product Strategy

**Document status:** Draft, part 11 of 16. Same disclosure standard as [Part 1](./01_executive_summary_and_foundations.md): every claim below is either a verified fact from the codebase/docs (cited inline) or an explicitly labeled recommendation. This part is written for both an investor deciding whether the product can carry the company to GCC, and an engineering leader who will inherit this backlog — so gaps are named with the same precision as strengths.

Supplify's core product-strategy fact, stated once so it does not need repeating in every section below: **the platform is far more built than sold.** 180 SQL migrations, 554 API routes, and 225+ backend / 100+ frontend tests (Source: `docs/onboarding/01-executive-overview.md`; migration count verified directly against `apps/api/db/migrations/*.sql`, 2026-07-01) sit behind a pricing catalog that, in places, promises more than the code enforces (`docs/product/tier-matrix.md`, §7). The roadmap below is organized to close that gap first, then extend the platform toward GCC, then extend it toward new supplier categories — in that order, because each phase is the precondition for the next being credible.

## 11.2 AI Strategy

**What is actually built, not aspirational.** Supplify's "Smart Reorder" system is real, shipped, and tier-gated — not vaporware (`docs/features/ai-smart-reorder.md`; confirmed directly in `apps/api/src/lib/ai-platform.js` and `apps/api/src/lib/ai/openai-provider.js`). It has two layers:

1. **Deterministic forecasting (Phase 1).** Statistical 30/90-day usage + lead-time coverage models, driven by `inventory_movement_log` consumption data with `receiving_line_item` and `order_item` as fallback signals, cached in a `reorder_forecast` table and refreshed nightly by cron. Available to **Gold and Platinum** (`smart_reorder` off on Silver/Free Trial); Platinum additionally adds weekday seasonality and trend adjustment.
2. **LLM assist (Phase 2).** A genuine, working OpenAI integration (`gpt-4o-mini`, JSON-mode responses) powers a natural-language **"explain"** endpoint (Gold+) and an **"ask"** endpoint (Platinum only). This is gated by three independent layers that must _all_ pass: the tenant's plan tier, the `ai_platform` feature flag (admin-overridable per tenant), and an environment kill switch (`AI_ENABLED`, default `false`). Usage is metered (`ai_requests_per_day`: 20/day Gold, 100/day Platinum) and every LLM call is audited (`reorder_ai_request_log`, tokens + latency + success).

**A material caveat for the marketing claim.** `AI_ENABLED` defaults to `false` and is not set to `true` in the committed Railway environment defaults (`apps/api/.env.example`; not found overridden in `deploy/railway/*/api.env`). Whether the LLM layer is actually switched on in any live environment today is **not confirmed by the documentation** — it is an operational toggle, not a code gap, but it means the founder should verify this explicitly before describing "AI-powered reordering" as live in a customer-facing conversation.

**What is still marketing, not product.** The tier matrix is explicit that "AI quick lists" (`quick_lists` = `ai_smart_automation` on Platinum) is **catalog-only** — it runs the identical scheduling logic as Gold's `full_schedule` value; there is no AI involved (`docs/product/tier-matrix.md` §7). "Advanced forecasting / custom reports" (the Platinum `reports` string) is likewise catalog-only. The honest split: **smart reorder forecasting, explain, and ask are real AI product; "AI quick lists" and "AI-driven custom reports" are not yet AI at all.**

**Realistic near-term opportunities (not hype):**

- **Supplier-side demand aggregation.** The same consumption data used for restaurant reorder forecasts is a direct input to supplier-side "what will my customers likely order next week" tooling — no new data collection required, only a new consumer of existing signals.
- **Bilingual catalog assistance.** Given the schema-level Arabic/English product fields (Part 1 §1.5), an LLM-assisted translation/normalization pass on supplier catalog data is a low-risk, high-leverage use of the same OpenAI integration already wired for reorder explain/ask.
- **Waste and dispute triage.** Turning today's boolean `waste_tracking`/`disputes_returns` features into LLM-summarized root-cause explanations reuses the existing "explain" pattern rather than inventing a new AI surface.

## 11.3 Integrations Strategy

**What exists today: infrastructure only, no external business-system integrations in production.** Direct codebase inspection (grepping `apps/api/src` and `apps/web/src`) found **zero references** to QuickBooks/Xero, Stripe, Twilio, or PayPal SDKs, and confirmed the following:

- **Payments:** `apps/api/src/lib/billing/providers/` contains only a `stub.js` (explicitly commented as a placeholder) and a `manual.js` path. No live processor is integrated.
- **WhatsApp:** `apps/api/src/services/whatsapp.service.js` is a stub returning `NOT_CONFIGURED`; the phone-normalization helper library it depends on (`lib/whatsapp.js`) is built, but the Meta Cloud API call itself is not wired.
- **Accounting export:** one real, partial asset exists — `apps/api/src/services/supplier-accounting-export.service.js` exports a **QuickBooks-compatible CSV** of invoices. This is a one-way, manual export, not a live QuickBooks/Xero API sync.
- **Everything else in the integrations table** (`docs/product/feature-catalog-full.md` §15) is infrastructure: Keycloak, PostgreSQL, Redis, MinIO/S3, Resend (SMTP), Web Push (VAPID), Socket.IO, Railway, Docker Compose.

## 11.4 Security

**Current posture is genuinely solid for pre-launch stage, and independently self-assessed as such.** A static security review (`docs/onboarding/15-security-review.md`, dated 2026-06-17) found **zero Critical** findings; 4 High, 6 Medium, 5 Low, all configuration/process items rather than code defects. Verified controls: Keycloak OIDC (authorization-code flow with CSRF state), httpOnly/secure/sameSite auth cookies, Helmet CSP/HSTS, CORS restricted to `WEB_ORIGINS` with credentials, parameterized SQL throughout (no injection surface found), and a genuinely two-layer authorization model — `requireFeature` (did the tenant pay for this module) is independent of `requirePermission` (may this specific user perform this action) — documented in `docs/architecture/access-control.md`.

**RBAC depth.** 52 permission keys across 18 domains (Orders, Invoices, Inventory, Reservations, Staff, Settings, Chat, Subscriptions, Catalog, Warehouses, Receiving, Payments, Fulfillment, Promotions, Customers, Growth, Driver, Admin), 7 restaurant + 9 supplier system roles, and **tenant-custom roles** gated behind the `advanced_roles` feature (Gold and Platinum only) — tenants can compose a role from the same permission checklist the system roles use (`docs/features/tenant-roles.md`). Audit logging is unified in an `audit_logs` table (migration `0046`) covering plan changes, limit overrides, and impersonation start/stop; admin impersonation itself is hardened (billing mutations explicitly blocked while impersonating, session force-cleared on logout).

**An architectural fact worth stating plainly, not a defect.** Multi-tenancy is **logical, not physical**: one PostgreSQL database, one schema, tenant isolation enforced by `tenant_id`/`tenant_type` columns and query-level filtering in `resolveTenantContext` middleware — not native Postgres row-level security and not per-tenant schemas. This is a normal, low-cost design choice at this scale, but any enterprise or GCC buyer's security questionnaire will ask "how is my data isolated from other tenants," and the honest answer is "application-layer, not database-layer" today.

**Gaps and next steps:**

- **Rate limiting is in-memory**, explicitly flagged as a "TODO: Redis for production" in `docs/architecture/hardening.md` — this will silently stop being correct the moment a second API replica is added, since limits won't be shared across processes. This should ship before any horizontal scale-out (see §11.5).
- **Secrets discipline is a process control, not a code-enforced one** — default secrets exist in `config/env.js` for local dev; there is no confirmed startup check that rejects them in production.
- **No compliance certification (SOC 2, ISO 27001) exists or is claimed anywhere in the documentation.** This should not be marketed until it is true. A SOC 2 Type I readiness program is a reasonable 12–18 month goal _once_ there is a resourced enterprise/GCC sales motion that requires it — starting it earlier spends scarce engineering time before it is commercially justified.
- **GDPR: partial.** Admin-side data export/delete tools exist; formal DPA (data processing agreement) obligations are not mapped (`docs/onboarding/15-security-review.md`, compliance notes). **Data residency: not enforced in code** — purely a deployment choice today. Both become real workstreams only once EU expansion (Part 14) is active, not before.

## 11.5 Infrastructure & Architecture

**Current state.** Railway hosts three fully isolated environments — dev, preprod, prod — each with its own Postgres, Redis, Keycloak realm, storage bucket, and payment mode (`docs/operations/railway-environments.md`). Both API and Web build from the monorepo root as a single Docker context (a documented and easy-to-misconfigure requirement). Local development runs the full stack via Docker Compose (Postgres 16, Redis, MinIO, Keycloak, mailpit, nginx) or native hot-reload. Object storage defaults to local disk unless `STORAGE_DRIVER=s3` is set — and the Railway deployment guide states plainly that **without a Railway volume, locally stored files are lost on redeploy** (`docs/operations/railway.md`) — production traffic should be on S3-compatible storage (MinIO/Cloudflare R2), which the code already supports.

**Real engineering maturity already shipped, not promised.** `docs/operations/railway-performance-report.md` documents nine dated phases of performance hardening: warm-kept DB connection pools, elimination of N+1 queries in RBAC/billing middleware, Redis-backed caching and singleflight request deduplication across roughly ten hot paths, an entitlements endpoint rebuilt from 26+ sequential queries into two batched, parallelized queries with a 90-second cache, gzip response compression, and frontend polling/prefetch tuning. This is evidence of active, iterative operational ownership — a materially different starting position than a team that has never had to make a production system fast.

**What breaks first at 10x tenant growth** (roughly Part 1's 18-month "low hundreds of tenants" horizon): a **single Postgres instance with no read replica**. Write-heavy, ever-growing tables — `customer_order`, `notification_log`, `audit_logs`, `reorder_forecast` — will show lock contention and I/O saturation on the primary before application compute becomes the bottleneck. **Fix path:** add a read replica for reporting/list-heavy queries, and time-partition the append-only log tables. Neither requires a data-model rewrite; both are operational additions to an already-tenant-scoped schema.

**What breaks first at 100x** (GCC-scale, thousands of tenants across multiple countries): **single-region deployment.** The performance report itself recommends confirming "the API service and Postgres database are in the same Railway region" as a manual check — there is no multi-region or data-residency product today. Cross-region calls are already measured to add 20–100ms; at GCC distances and volumes this becomes a real latency and availability problem, not a rounding error. **Fix path:** regional API/Postgres pairs per market. Because tenancy is already fully `tenant_id`-scoped rather than hard-coded to one deployment, this is a genuine re-platforming project (provision regional stacks, route tenants to their region), not a schema rewrite — a materially cheaper problem to solve than it would be in a single-tenant-per-database or hard-coded-region architecture.

**A standing risk that compounds with the above:** in-memory rate limiting and the in-memory cache fallback (used automatically when `REDIS_URL` is unset) will silently lose correctness the moment more than one API replica is required — this must be resolved (see §11.4) before any horizontal scale-out, not after.

## 11.6 API Strategy

**Current internal surface.** 554 API routes (`docs/onboarding/01-executive-overview.md`), consumed today only by the web SPA and a sibling native mobile app. A `/api/public/*` surface exists, but it is scoped narrowly to unauthenticated guest reservations and staff self-service (magic-link login, PTO requests, clock in/out) — not a general-purpose, merchant-facing developer API.

**The disclosed gap, confirmed by code, not just documentation.** `api_integrations` (off on Silver, `api_key_access` on Gold, `full_api_webhooks` on Platinum) and the notification string `email_whatsapp_webhook` are sold entitlements with **no backing implementation**: there is no API-key issuance table or authenticated route in the codebase, and no webhook dispatch/delivery subsystem exists anywhere in `apps/api/src`. This is the single highest-visibility item in the catalog-only backlog, because "does your API actually work" is the kind of claim a technical buyer (a chain's IT team evaluating Platinum) will test directly rather than take on faith.

**A real plan to close it, sequenced:**

1. **v1 read-only public API** — orders, invoices, catalog, inventory levels, scoped per tenant, authenticated by an issued API key (new `api_key` table + a Settings-page issuance UI). This is additive: it reuses the existing RBAC and tenant-resolution middleware rather than building new authorization logic.
2. **Redis-backed rate limiting and audit logging for API-key traffic**, reusing the same patterns already built for the rest of the app (see §11.4).
3. **Outbound webhook delivery system** — event types (order status change, invoice issued, dispute opened), signed payloads, retry/backoff, delivery log. This is the largest genuinely new subsystem in the list; everything else above is extension of existing infrastructure.
4. **Public OpenAPI documentation** — the codebase already generates route-level OpenAPI internally (`pnpm openapi:gen`, per the feature catalog), so publishing a developer-facing doc site is a comparatively small final step.
5. **Gate v1 scopes behind the existing `api_key_access` / `full_api_webhooks` feature strings** so that, for the first time, what is priced matches what is enforced.

Until step 1 ships, sales conversations for Platinum should not represent full API/webhook access as available today — consistent with the disclosure stance this document and Part 1 both take.

## 11.7 Scalability

**Technical.** The architecture — logical multi-tenancy, a Redis-cacheable middleware stack, and (once rate limiting moves to Redis) horizontally replicable API instances — is a reasonable foundation to reach 10x tenant growth without a rewrite. Reaching GCC-scale (100x, multi-region) is a genuine infrastructure project, not a data-model rewrite, precisely because tenancy is already fully `tenant_id`-scoped rather than baked into a single region or database (§11.5). The disclosed backlog items in this document (catalog-only closure, add-on billing automation, payment gateway integration) are scoped, known engineering work — not open-ended unknowns that could derail the timeline.

**Organizational.** Can the current team and architecture support Part 1's 18–24 month GCC objective? The architecture itself is not the constraint: the bilingual schema, the tenant-type-agnostic catalog model, and the enumerated backlog above are all things a team can plan against. What actually determines feasibility — team size, hiring plan, and sustained engineering velocity — is **not known to this document** (see the sanity-check note below) and must be validated separately before this timeline is treated as a commitment rather than a target.

## 11.8 Innovation

Three product bets that are genuinely differentiated because they extend something Supplify already has, rather than describing a feature any competitor could copy in a sprint:

1. **Cross-marketplace demand signals from the unified two-sided data model.** Because Supplify already captures both restaurant consumption/order data _and_ supplier fulfillment/inventory data in one schema, it is structurally positioned to build demand signals neither a single-sided ordering tool nor a supplier-only ERP can see (e.g., aggregated, anonymized category-level demand trends across nearby restaurants). The `reorder_forecast` infrastructure (migration `0166`) already exists as single-tenant input; extending its inputs to anonymized cross-tenant aggregates is additive engineering on top of a working system, not a new AI platform built from zero.
2. **Bilingual-by-schema as a GCC-speed advantage.** Arabic/English product fields exist at the schema level today (Part 1 §1.5), not as a translation layer bolted onto a US/EU-built product. Most named competitors (Part 4, forthcoming) are built for US/EU markets and would need to retrofit Arabic support at the data-model level, not just the UI layer — Supplify can ship a genuinely Arabic-first supplier catalog experience faster than they can catch up, because the content itself (not just the chrome) is already bilingual.
3. **Trust infrastructure as the foundation for real central purchasing.** "Central purchasing" is listed today as a Platinum catalog-only string with no differentiated behavior (§11.1, §11.6). But the underlying primitives — branches modeled as linked tenant accounts under one org, with org-level roles including a Regional Manager already in the RBAC model (`docs/architecture/tenancy.md`) — mean a real consolidated cross-branch ordering and negotiated-pricing engine is a natural extension of what is already built, not a new product category. Few point-solution competitors have comparable multi-branch RBAC depth to build this credibly, which makes it a defensible bet rather than a commodity feature.
