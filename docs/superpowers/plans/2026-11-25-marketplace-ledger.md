- A8: Ruling: behaviour is covered by the real-PG suite (`supplier-intel.pg.test.js`), not new mocked unit tests per service. The changes are SQL predicates, which mocked `query` cannot exercise. Existing unit tests were adjusted only where a positional mock met the new check (`supplier-pain-killer.test.js`, `supplier-reorder-intelligence.service.test.js`). Cost if wrong: none for behaviour; less unit-level isolation.
- A8: Ruling: `src/routes/supplier-ops.routes.test.js` does not exist. The "CSV exports stay order-scoped" assertion lives in `supplier-intel.pg.test.js` against `exportInvoicesCsv`. It passes on the old code too, because this was a review item, not a change. Cost if wrong: none.
- A8: Ruling: cross-sell pair evidence still uses every customer's orders (anonymous aggregate). Only the named suggestion rows are restricted to followers. Cost if wrong: a supplier can infer co-purchase patterns from lapsed customers, without names.
- A8: Ruling: a block skips cadence reminders for both parties. An unfollow only stops the supplier's notification; the restaurant still gets its own "you usually order X" reminder. Cost if wrong: an unfollowed restaurant gets reminders about a supplier it must re-follow to order from.
- A8: Ruling: the snapshot-first COALESCE swap is applied where the brief names it: packing slip JSON and PDF, and route stops. Other `COALESCE(r.name, o.customer_contact_snapshot->>'name', …)` sites (order list, detail, board, calendar) are unchanged. `customer_contact_snapshot` is only written for consumer (public-sales) orders, so for restaurant orders the live name is shown either way; the address now comes from `delivery_location_snapshot.address`. Cost if wrong: the live restaurant name, rather than the name at order time, shows on those other screens.
- A8: Ruling: `get_followed_suppliers` now reads `supplier_follow.supplier_org_id` and excludes blocked organisations, instead of joining through `supplier_follow.supplier_id`. Cost if wrong: none.

- A7: Ruling: added `canSeeRestaurant` (spec §6.4 names it; follow AND not blocked, non-UUID → false) and `lockAndAssertRestaurantVisible(client, restaurantId, supplierId)` to `lib/relationship.js`, so the shared lock and re-check are one call for manual orders, contracts and (Task 9) sponsorship offers. Cost if wrong: none.
- A7: Ruling: PATCH of an unknown contract id answers 404 `RESTAURANT_NOT_AVAILABLE`, the same body as a contract whose restaurant no longer follows, rather than `NOT_FOUND` "Pricing not found". "Same 404 for not-found and not-allowed" requires one body. Cost if wrong: a supplier editing a deleted contract sees "restaurant not available".
- A7: Ruling: contract DELETE (deactivate) is not relationship-gated. Removing a hidden contract reveals nothing and only reduces what the supplier holds. Cost if wrong: a supplier who guesses a hidden contract id can deactivate it.
- A7: Ruling: a follower with a foreign or unknown branch id still gets the existing 400 `DELIVERY_LOCATION_INVALID`. The no-probing rule protects restaurants the supplier cannot see, and a follower's branch list is already visible to the supplier through delivery locations. Non-followers get the 404 before any branch lookup (tested). Cost if wrong: a follower's branch ids could be probed by that same supplier.
- A7: Ruling: fixed a pre-existing bug. `GET /api/restaurant-pricing` with no status filter bound the timezone as `$2` without referencing it, so real PG rejected the query (unit tests mocked the DB). A `$2::text IS NOT NULL` condition keeps it referenced. Cost if wrong: none.
- A7: Ruling: the customer list no longer includes past customers who never followed or who unfollowed, per spec §6.2 item 6. The supplier "new conversation" picker reads this list, so it now offers followers only. Cost if wrong: suppliers lose quick access to lapsed customers outside their order history.

- A6: Ruling: the chat PG test loads `socket.io-client` from `apps/web`'s dependencies via `createRequire` rather than adding it to the API package. Cost if wrong: the test breaks if web drops the dependency.

Cost if wrong: old clients that open `fileUrl` directly now need the auth cookie or header (web sends the cookie; mobile is updated in Task 13).
- A6: Ruling: an existing conversation stays readable after an unfollow. Re-opening it (POST create) returns it instead of a 403, so history and order-tagged messages remain reachable; only a brand-new conversation needs a follow. Cost if wrong: an unfollowed restaurant still sees the conversation in its list (read-only).

Cost if wrong: an order with a sibling branch cannot be discussed in this branch's conversation.
